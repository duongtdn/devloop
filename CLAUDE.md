## What this plugin is

`devloop` is a Claude Code plugin (package scope `@noetaris`) that automates a full sprint lifecycle: planning, execution (TDD workflow), PR review, and sprint close. Users invoke top-level skills; skills orchestrate sub-agents that each own a narrow role.

The main workflow runs at two altitudes:
- **Inner loop** (human-*on*-the-loop): autonomous execution — `run --auto` (one issue, run to completion: by default merges locally with no PR), `sprint` (the same across the whole sprint, merge-as-you-go). Gates don't stop; every decision + reasoning is logged to `context.md` Zone 2 for later audit; the run stops-the-line rather than fake a judgment it can't make. Delivery is a separate axis: `--pr` opts into a GitHub PR — in human mode the run then halts at the open PR for review; in auto mode it merges the PR through.
- **Outer loop** (human-*in*-the-loop): the `review` conversation — task scope (`review 42`: explain, demo, accept→merge or rework→`replan`) or sprint scope (walk un-accepted tasks, then reconcile/retro/tag/close). Human acceptance is recorded as a `✓accepted` annotation on the sprint-file issue line — orthogonal to the checkbox, since autonomous execution merges/closes issues before anyone reviews them. Substantive rework is always a **new** issue cross-linked to the shipped one (`Rework of #N` / `Rework tracked in #M`), never a reopen; a fix that changes **no behavior** is instead **patched in place** (see the patch bullet below).

The default (no flags) remains fully human-gated: every gate pauses for confirmation.

Above both sits a third altitude, the **tight loop**: `tinker` — a developer and the AI at the keyboard with the app *running*, the AI writing the code on the developer's behalf while they direct and review it. The other two loops are anchored to a **plan** written earlier (an issue, a sprint); this one is anchored to the **running system and the human watching it**. **Size is not its limit** — a session may retune a constant or build a feature; the small no-behaviour fix found mid-review is `review`'s patch, not tinker's charter. Its value over a bare prompt is that delivery follows `run`'s QA and process, so the code does not drift from the architecture (a behaviour change is proved by a red-verified test, placement is looked up, recorded decisions still bind, a bigger instruction is planned and reviewed, the project's checks gate every commit); what changes is *who supplies the plan* (the human, one instruction at a time) and *who holds the gates* (the human, present). See the `tinker` bullet under [Key conventions](#key-conventions).

Cutting across all of it is `docs` — the one thing devloop writes **for humans to read**. Everything
else it records is transactional (an episode, an issue, a decision, a sprint), so nothing answers
*what is this system right now*; the AI never notices because the `context` agent rebuilds a
task-shaped slice of that answer on every issue and throws it away, and a human cannot. See the
`docs` bullet under [Key conventions](#key-conventions).

Beside that sprint machinery sits one **separate track**: `vibe` — a small greenfield app built with a
non-technical owner present, no GitHub, no sprints, and no TDD (proof is deferred to a tracked ledger
and harvested before the app is shared). It borrows the agents and shares `roadmap`'s discovery spec,
but it is not the sprint loop with flags — see the `vibe` bullet under [Key conventions](#key-conventions).

Read-only; cites, never invents
```
│   ├── doc-writer.md            # Writes ONE leaf doc from its map node + the architecture doc + a component survey. Follows the tone contract; never invents a path, never creates a node, has no Bash so it cannot commit
│   ├── doc-critic.md            # Reads a drafted human doc and returns where a new developer would be stuck (uncited claim, undefined term, wall, hedge, unbound diagram node) + the fix. Mute; Read-only; fresh instance per doc
│   ├── pr-triage.md             # Classifies a PR's review intensity (light/full) from the nature of the diff.
│   ├── reviewer.md              # Reviews diff (reasoning only, never posts). Modes: review (run), pr-review (same rubric + test-adequacy, graded for a merge candidate), critique (uphold/drop + may raise a blocker pass 1 missed), fix-review (scoped fix verification)
│   └── scaffolder.md            # Creates repos, bootstraps project structure, commits to main
├── docs/
│   └── field-reports/           # Dated post-mortems; each one is why a rule below is worded the way it is
└── CLAUDE.md                    # dev-only — not shipped; no skill or agent may depend on it
```

**`CLAUDE.md` is for developing this plugin and is not deployed.** An installed skill or agent never sees it, so each must be self-contained: every rule *and* every reason the model needs to apply that rule correctly lives in the skill or agent file. This file may explain why a rule exists; it must never be the only place a rule, or the reasoning a rule depends on, is written.

Skills live in `skills/<name>/SKILL.md`. Agents live in `agents/<name>.md`. The `name` field in `plugin.json` sets the skill namespace, so all skills are invoked as `/devloop:<skill-name>`.

## GitHub integration strategy

The plugin uses the **official GitHub MCP server** for all standard operations (issues, PRs, branches, adding labels to issues) plus a **bundled `github-extras` MCP** (`bin/github-extras.js`) for the operations the official server does not cover — milestones and repository label management:

| Operation | Tool source |
|---|---|
| List/create/close issues, add labels to issues | Official GitHub MCP |
| Create/merge/update PRs | Official GitHub MCP |
| Create/list branches | Official GitHub MCP |
| Read a single label (`get_label`) | Official GitHub MCP |
| **Create milestone** | Bundled `github-extras` MCP |
| **Read / list milestones** (state, `due_on`, issue counts) | Bundled `github-extras` MCP |
| **Assign issues to milestone** | Bundled `github-extras` MCP |
| **Clear an issue's milestone** (`milestone_number: null`) | Bundled `github-extras` MCP |
| **Close milestone** | Bundled `github-extras` MCP |
| **List repository labels** | Bundled `github-extras` MCP |
| **Create repository label** | Bundled `github-extras` MCP |

The official server has **no milestone tools at all** — not even a read — so *every* milestone operation, including simply looking one up, goes through the bundled server (list with `state: all` and pick by number; it returns `state`, `due_on`, and open/closed issue counts). It likewise has no tool to *list* or *create* repository labels (only `get_label` reads one by name). The bundled server fills both gaps.

**Clearing a milestone is a first-class operation, not an edge case** — it is how `review` carries an issue over or sends it to the backlog, and how `replan` drops one, and the `issue-selector` only sees issues with *no* milestone, so an uncleared carry-over doesn't carry over: it vanishes from the process. The official server cannot express it (its milestone field is typed `number`, which rejects `null`; omitting it leaves the milestone untouched), so the bundled server's milestone-assignment operation takes `milestone_number: ['number','null']` — `null` removes the issues from their milestone. It stays **required**, so no accidental omission ever clears one. Never fall back to `gh` for this: `gh` is not a declared devloop dependency, and a skill that reaches for it fails on any machine with a valid token but no `gh` login (`docs/field-reports/2026-07-13-cannot-clear-milestone.md`).

Both MCP servers are declared in `.mcp.json` at the plugin root and start automatically when the plugin is active. The official GitHub MCP is wired as the remote server `https://api.githubcopilot.com/mcp/` with `Authorization: Bearer ${GITHUB_TOKEN}`; the bundled `github-extras` stdio server reads the same `GITHUB_TOKEN` from the environment. A single token covers both — the user just exports `GITHUB_TOKEN`.

**Never hardcode an MCP tool's literal name in a skill or agent.** The table above documents *capability → server* for humans; it is not a literal call target. For a plugin-declared MCP server, the harness composes the runtime tool name with an internal, undocumented prefix (observed: `mcp__plugin_<pluginName>_<serverKey>__<tool>`, not the plain `mcp__<serverKey>__<tool>` form the official settings.json permission-rule docs describe) — and it silently differs by host and can change across Claude Code versions. An agent whose `tools:` allowlist or prompt names a specific literal tool string that doesn't match at runtime doesn't just fail cleanly — the model tends to fabricate a plausible-looking result instead of erroring (confirmed via a minimal reproduction plugin). Every agent and skill that touches GitHub must instead: (1) describe the *operation* in plain language and let normal tool selection find the right binding by purpose/description, never by asserted name; (2) omit MCP tools from an agent's `tools:` allowlist entirely (an explicit allowlist entry only works if it happens to match the composed runtime name, which is not safe to assume); (3) carry an explicit instruction to never fabricate — if no suitable tool can be found or a call fails, stop and return `ERROR: [reason]` rather than guessing.

## Central artifacts (written to user's working repo)

| Path | Purpose |
|---|---|
| `.context/product-brief.md` | What the product *is*, from the owner's side: one sentence, the domain nouns in their words, named users, one scenario walked, what it does, **what it does NOT do**, an ASCII shape, and `⚑` on anything still guessed. Technology-free on purpose. **Written in the language the owner is spoken to in** — it is a document *for* them, its whole method is drafting a thing they correct, and its most falsifiable section is only falsifiable by someone who can read it; where the code is written in another language the nouns carry an identifier column, the one recorded translation every other reader copies. Written by `vibe` and `roadmap` through the shared `skills/vibe/ba-spec.md`; readable by every skill and agent. Shared project record. |
| `.context/devloop-profile.md` | Operational manifest: build/test commands and test layout. Shared project record. Bootstrapped by `roadmap`; read by `plan` and `run`; written back by `run` (scaffold + newly-filled fields). Holds commands only — never stack/conventions (those stay in CLAUDE.md). |
| `.context/devloop-journal.md` | **The project's episodic memory** — one line per finished episode of work, any altitude: `date · mode · outcome · code areas · what-and-why → the record`. Append-only, flat, never rewritten. Written by `run` (shipped/blocked), `tinker` (hand-tuned), `vibe` (per demo point), `review` (patch, sprint close), `architect` (decided/superseded), `abort` (abandoned). **Read by the `context` agent on every issue** — the entries whose areas intersect the work become Zone 1's `What happened here before`. Written by `tinker` on an override only (a tweak that took the test-first path proves itself and adds nothing, which is what keeps this file short and honest). Read by `review` at sprint close (each open row offered as a backlog issue) and by `plan` when scoping. In the **vibe** track the rows go to `vibe.md`'s ledger instead — one reader, one file. Shared project record. |
| `.context/tinker/<date>-<slug>/context.md` (+ `logs/`) | One `tinker` session — **named `context.md` on purpose**, because the `coder` reads `$WORK_DIR/context.md` and a session record under any other name is one the agent doing the work never sees. Zone 1 (seeded at open from the session goal, extended when an instruction reaches a new area — the ADRs binding the area, where new code goes, what the journal already knows) + Zone 2 (one append-only entry per tweak: what, **why**, the rung call, the proof, the SHA). Written by `tinker` only. |
| `.context/devloop-baseline.md` | Accepted-failure allowlist: checks known to fail and accepted until a real fix lands. Shared project record. Written by `run` on user decision (needs a tracking issue); read by the `test-runner` agent to classify failures as accepted vs new. Lets the green-check gate mean "no *new* failures," not zero. |

Append-only — a changed decision is a new superseding ADR; only the old `Status:` line mutates. `index.md` is the retrieval surface: one hook line per ADR naming the code area it governs, scanned by the `context` agent to surface bearing decisions as Zone 1 constraints. Shared project record. |

Clean prose and mermaid diagrams; **no machine metadata of any kind** (a reader opens a document, not a record). `.context/` is the machine's memory, this tree is the human's. Written by `docs` through `skills/docs/docs-spec.md`. Version-controlled — it is for whoever clones the repo. |

A **snapshot**, overwritten each run (derived, so not history). Written by `docs` in audit mode; read by `plan` when scoping and offered by `review` at sprint close. |
| `.context/docs-work/` | Transient working area for a `docs` episode — the `surveyor`'s `survey.md` and one `<node id>-survey.md` per component. Raw material, not a record: safe to delete between runs. |
| `.context/sprints/master-plan.md` | Project sprint map: vision, sprint themes, goals, statuses. Created and updated by `roadmap`. `plan` writes `Status: active` and `Sprint file:` per sprint; `review` writes `Status: completed`. |
| `.context/sprints/sprint-N.md` | Sprint execution file. Checkbox list read/updated by `run`; lines amended by `replan`; `✓accepted` annotations written by `review`. Line grammar in `skills/plan/plan-spec.md`. |
| `.context/sprints/state/.lock` | Concurrency guard: `holder`, active issue/PR/session, PID, start time. Held by `run`, `pr-fix`, `vibe` (during a build stage), and `tinker` (for the session) — one tree, one writer. |
| `.context/sprints/state/issue-{N}.md` | Control plane for one in-progress issue: phase, position (`task_index`/`phase_step`), branch, confirmed plan, task list, log, and a pending-gate payload (lets a gate re-present on resume without re-running its agent). |
| `.context/sprints/work/issue-{N}/context.md` | Central knowledge file. Zone 1: retrieved facts (owned by `context`). Zone 2: append-only decision timeline — `planner`/`test-writer`/`coder`/`reviewer` and `run`'s gates each append a self-contained, script-timestamped entry; never edited. **Append-only is enforced by the tool, not by prose**: entries go in via a shell append (`cat >>`), never `Edit`, which lands wherever its anchor matched — observed putting a coder entry inside Zone 1. Resume reads the *last* entry, so an inserted one makes the last stale and can mark a step done that never ran. Each entry carries its own freshly derived `$NOW`; a reused timestamp leaves a batch of entries with no order, in which a misplaced one is undetectable. **The entry header (`### [$NOW] · author · ref`) is restated literally at all nine agent write sites, never pointed at** — a pointer ("format per that section") loses to the nearest visible heading, and the observed corruption was the Zone 2 *section* header (`## Zone 2 — Agent notes`) copied with the timestamp substituted, which destroys the resume receipt (no author to match, and `##` opens a second Zone 2). For the same reason `context` writes one correctly formatted **seed entry** (its depth tier) rather than leaving Zone 2 empty: a live example at the write site outranks a legend in a comment. |
| `.context/sprints/work/issue-{N}/plan.md` | Implementation plan from the `planner` agent. |
| `.context/sprints/work/issue-{N}/test-plan.md` | Test strategy: unit scenarios per task + E2E scenarios per flow. |
| `.context/sprints/work/pr-{repo}-{N}/context.md` | Standalone PR work dir (full-tier `pr-review`/`pr-fix` on a PR with no usable issue work dir). Built by `context` (`pr` mode). Part of `run`'s per-issue working area, like the rest of `work/`. |
| `.context/sprints/sprint-N-review.md` | Sprint retrospective from `review` — including **Shipped without proof** (open `devloop-unproven.md` rows) and **Changed outside the issue list** (journal lines no issue covers). Written for nobody until the journal made it reachable: `plan` now reads the previous sprint's *What to improve* and *Process feedback* when scoping the next one, as suggestions the human is free to ignore — never as constraints. |
| `.context/vibe/vibe.md` | The whole state of a `vibe` project in one file the owner could open and read: goal, the `Talking:`/`Writing:` languages, the technical Decisions (product question → decision → why → can-we-change-it-later → one technical line), the demo-shaped Plan with its `vibe-demo-N` tags and the `At:` cursor, the **What we haven't proved yet** ledger, Parked items, and a log carrying every plan change with its why. Written entirely in `Talking:` — a state file the owner cannot read is one that is not doing its job. `vibe` is the only writer; `tinker` reads its language fields and adds ledger rows. |
| `.context/vibe/work/m<N>/context.md` | Per-milestone knowledge file for a `vibe` build — Zone 1 assembled by the skill itself (there are no GitHub issues for the `context` agent to anchor to), Zone 2 appended by `coder`/`reviewer`/`vibe`. Same two-zone shape and same append-only rule as `run`'s. |

`.context/sprints/work/` and `.context/sprints/state/` are `run`'s per-issue working area; `profile`, `baseline`, `master-plan`, `sprint-N`, and the sprint reviews are shared project records. **Whether any of `.context/` is version-controlled is the user's choice — devloop neither assumes nor enforces a gitignore policy.**

**A diff range is a parameter, not an inference.** `$BASE`/`$HEAD` are enumerated at every `reviewer` invocation (`run`, `pr-review`, `pr-fix`) exactly as `$CHECKS` is at every `coder` one — the skill holds the verdicts, the agent computes the diff, so the range *is* the review's scope. It fails the way a guessed MCP tool name does rather than the way a missing file does: an improvised range returns confident, well-formed findings about the wrong code (or `FINDINGS: 0` on an empty one), and nothing tells the caller apart from a clean review. The agent returns `ERROR: no diff range given` rather than guess. Every mode that computes a diff uses **three-dot** (`$BASE...$HEAD`) — merge-base, so only the branch's own contribution is in scope; `$BASE` moves under an open branch (merge-as-you-go; `run` doesn't rebase until merge, so a branch reaching review is routinely behind), and two-dot would present that drift inverted, as deletions. Only `fix-review`'s `$FIX_RANGE` is two-dot, correctly: it is a linear range of fix commits on one branch.

**`$WORK_DIR` and `$LOG_DIR` are always passed to agents as absolute paths**, anchored to `$REPO_ROOT` captured once at `run` startup (`skills/run/SKILL.md` S1) — never as a bare `.context/...` string. `coder` and `test-runner` run project check commands via Bash, and in a monorepo those commands often `cd` into a subpackage (e.g. `cd apps/web && npm test`); that `cd` persists for the rest of the agent's Bash session, so a relative log path resolved afterward would land under the subpackage instead of `.context/`.

## Key conventions

- **Skill frontmatter**: every `SKILL.md` must have a `description:` field. Use `$ARGUMENTS` for user input after the skill name.
- **Agent frontmatter**: `name`, `description`, `tools` (allowlist), `disallowedTools`. **No `model:` field** — model choice is left to the host tool so the plugin runs unchanged on any agent runner (Claude Code, Copilot, Codex, …); an agent that genuinely needs a cheaper/faster tier says so in prose for the host to honour, never by naming a vendor model. Agents cannot declare `mcpServers` or `hooks` — plugin-level MCP covers that. Exception: agents that touch GitHub (`backlog-triage`, `issue-selector`, `context`, `scaffolder`, `test-runner`) omit MCP entries from `tools:` on purpose — see [GitHub integration strategy](#github-integration-strategy) for why hardcoding an MCP tool name is unsafe here.
- **Conversational skills** (`roadmap`, `backlog`, `architect`, `plan`, `replan`, `review`, `abort`, `tinker`, `vibe`): pause at every human gate with explicit confirmation before any destructive action. `tinker` is the one whose *cadence* differs — its gate is per instruction and answerable in two seconds, not a panel — but the rule is the same: nothing lands without an explicit yes.
- **Autonomy and delivery** (`run`): two orthogonal axes, both set at invocation, persisted in the state file, governing on resume. **Autonomy** — `autonomy: human | auto`, set by `--auto`; in auto mode gates decide-and-log instead of pausing (Zone 2 entries attributed to `run (auto)`), spikes are preferred over reasoning for load-bearing assumptions, the run **stops-the-line** — logs a blocker and exits — wherever human-mode would escalate, and it **runs to completion (merges)** rather than halting (the human reviews afterward in the outer loop). **Delivery** — `delivery: direct | pr`, set by `--pr`; **direct** (default) merges the branch into base locally with no PR, **pr** opens a GitHub PR. Only the **human + pr** cell halts before merge (at the open PR); every other cell merges within the run. `sprint` drives plain `run --auto` (direct). Both persist in the state file and govern on resume — a resume flag cannot switch them, with **one exception in one direction: autonomy downgrades `auto` → `human`** when a resume omits `--auto`. That is the exit from every auto-mode blocker: each stop happens precisely because the run met a judgment it isn't entitled to make, so a resume that couldn't take the human's seat would re-take the same exit forever (a manual-workflow issue is the purest case — auto-mode can *never* complete it). A downgrade only adds oversight, so it needs no new authorization; the upgrade is refused, because authorization to merge unattended is granted at a run's start, not retrofitted onto half-done work. One asymmetry inside auto mode: when it approves a **design**, the Zone 2 entry is marked **`AUTO-APPROVED — NO HUMAN REVIEW`**. A code diff merged unattended is still there to be read afterwards; a design's **silence** is not, because every later issue measures conformance *against* that document, so whatever it failed to say is never checked again by anything. The marker is how the outer loop knows which binding documents nobody read. Zone 2 only — never an annotation on the sprint file, whose line markers other skills own.
- **Sprint amendments** go through `replan` only — it and `plan` share `skills/plan/plan-spec.md` (issue-body template, DoD-by-type, sprint-file line grammar) so formats never drift. `review` records human acceptance as a `✓accepted YYYY-MM-DD` annotation on the sprint-file line (only `review` writes it; only `run` ticks the checkbox).
- **State machine** (`run`): a resumable phase spine (`context → [design → gate-design] → plan → gate-plan → build → e2e → review → validate → [gate-deliver (direct) | gate-pr → pending-review (pr)] → merge`). The active **workflow** (feature/bugfix/design/scaffold/manual, chosen from labels and confirmed at gate-plan) selects which phases run. The optional **design** phase produces an implementation guide / decision doc (`design.md`) — always for the design workflow, and for a feature/bugfix when the planner raises `NEEDS-DESIGN`. The **manual** workflow handles issues with no code to build (configure DNS, obtain a sign-off, manual QA) — the planner raises `MANUAL` from the plan phase and run carries the issue to done through a single confirmation gate (`gate-manual`): no branch, tests, or PR. The `designer` authors it and a fresh `designer` instance critiques it against named criteria; load-bearing assumptions can be proven with a throwaway `coder` spike before the gate. Reads `.context/sprints/state/issue-{N}.md` to resume from the last recorded phase; never re-runs a completed phase — **or a completed step within one**. Gates are resumable too — the panel-building payload is persisted before a gate is shown, so a crash at a gate re-presents it from disk rather than re-running the agent.
- **The state file's two fields answer two different questions** — `phase:` is written on **entry** (so a crash resumes into the right phase, not the previous one); `phase_step:`/`task_index:` are written on **completion**, as the first thing done with an agent's return, before it is parsed. Written the other way round they make "about to invoke the reviewer" and "the reviewer finished" the same value on disk, and a resume then re-runs the loop's most expensive agent — which is not a retry: a fresh reasoning instance returns a *different* finding set, and the resulting ad-hoc union of two pass-1 reviews is what the gate then decides from. **The residual crash window** — agent returned, run hadn't written yet — is closed by reading the **last** Zone 2 entry (one `tail`, never a scan or a `git log` reconstruction): appending agents write their entry *before* returning, so it is a receipt more durable than run's own bookkeeping. It is trusted only if its author, mode, and a timestamp `≥` the phase's start line all match, so the check fails toward re-running rather than toward skipping a review nothing downstream would miss. **Startup itself never spawns a search agent** — every fact it needs is at a named path, an absent file *is* an answer, and the stale `.lock`'s `issue:` field is captured before the lock is deleted rather than reconstructed afterwards.
- **Project profile** (`.context/devloop-profile.md`): the single source for build/test commands — `run` never guesses a command, and never hardcodes which QA runs. It executes exactly the checks the profile lists (`$CHECKS`), locally, as the back-half at every rung. A heavy check the project's CI owns is simply left out of the profile — in `--pr` mode branch protection still gates the merge on CI; `direct` mode has no CI, so the listed checks are the whole gate. `roadmap` bootstraps it, `run` maintains it. Commands only; stack/conventions live in CLAUDE.md (auto-loaded).
- **Rung — process weight is the planner's call, sized to the task** (`run` build phase): the planner returns a rung in `plan.md`, orthogonal to the phase set, chosen by two questions — *does the change add/alter behavior — and if not, does it touch any checkable surface at all?* Four rungs:

  | Rung | When | Proof | Path |
  |---|---|---|---|
  | **`STANDARD`** | new/changed behavior | a **new test, red-verified** | full TDD, two-pass review |
  | **`REFACTOR`** | no new behavior, but the code is used and is being restructured | **coverage** — the existing suite must stay green | collapsed front half, single-pass review |
  | **`EXPRESS`** | no new behavior, nothing live depends on the touched code | **triviality** grep | collapsed front half, single-pass review |
  | **`TRIVIAL`** | no new behavior **and no checkable surface** — whole inert files that feed no `$CHECKS` command (docs, `LICENSE`, `CHANGELOG`) | **inertness** — verified *after* the edit on the real `git diff` (`--name-only` ⊆ the named targets) | no test, **no review, no validate, no e2e**; back half trimmed to the checks a path feeds (usually none) |

  The `EXPRESS`/`TRIVIAL` line: a comment/whitespace edit *inside* executable source is **not** `TRIVIAL` (the file feeds a check → `EXPRESS`) — that's what keeps a load-bearing comment (`@ts-expect-error`, a doctest, JSDoc under `checkJs`) from slipping past a check that can see it. **Lightweight ≠ unverified:** the regression/fitness back half (coder runs its check set; `test-runner` independently re-runs the tests) runs in full at every rung *with checkable surface*, and `validate`/reachability runs for all but `TRIVIAL` (for the collapsed rungs it is the *primary* evidence; `TRIVIAL` exposes no symbol to trace). `TRIVIAL` is the one rung that trims the back half itself — a principled exception, not a hole: it omits only checks that provably cannot observe an inert file, and the moment the diff touches a checkable path it auto-bumps. **`run` never picks the rung** — the planner does, from context, like `NEEDS-DESIGN`; a mis-called rung **auto-bumps up** (one-way ratchet): `TRIVIAL`→`EXPRESS` (a touched path is checkable), `EXPRESS`→`STANDARD` (triviality proof fails or a `new` failure appears; a `REFACTOR` that breaks a test is a regression to fix in place, and `THIN` coverage surfaces / stops-the-line rather than refactoring blind). The human may reshape the rung at gate-plan (logged), which **re-invokes the planner** with the mandate — a rung is a flag *plus* the artifact licensing it (`test-plan.md` / `Triviality proof` / `Coverage` / `Inertness proof`), and **only the planner writes those** (run inventing one is run doing the planner's job). The user sets the rung; they don't assert its evidence (a mandated `REFACTOR` over untested code still comes back `Coverage: THIN`). Auto-mode accepts the planner's rung and never downgrades on its own initiative.
- **Context depth is self-calibrated, deepened on demand**: the `context` agent sizes retrieval (`minimal`/`standard`/`deep`) to the issue and biases light; the planner raises `NEEDS-CONTEXT: [specific fact]` when Zone 1 is too thin, and `run` re-invokes `context` in `deepen` mode to append exactly that gap (bounded at 2, then `$CONTEXT_FINAL`). Same delegation rule as everywhere: `run` doesn't assess how much context an issue needs — the specialist signals, `run` reacts. Downstream agents lack GitHub MCP, so `deepen` is also their only path back to a related issue's body.
- **Green-check gate**: "no *new* test failures," not zero failures. Accepted known-failing tests are tracked in `.context/devloop-baseline.md`, and their ids (`$ACCEPTED`) must be passed to **every agent that runs the suite** — the `coder` as well as the `test-runner`. A suite command exits non-zero on an accepted failure just as it does on a real one, so a coder without `$ACCEPTED` can never reach green in a project that has baselined anything.
- **Two runs, two purposes**: the `coder` runs the suite as a *feedback loop* ("should I keep working?") and its green is **provisional** — it is a self-report from the one agent that both wrote the code and wants it to pass. The `test-runner` runs it as the *verdict* (classification against the baseline + independent verification). Skills believe the `test-runner`.
- **Red is verified, not assumed**: `test-writer` may not run tests and `coder` only ever reports green, so without a check *nobody observes the failing state* and "the test failed first" is an unverified claim. `test-runner` (`mode: red`) runs the fresh tests alone and returns `RED` (real assertion failure), `RED-SETUP` (failed on a broken import/fixture — not a meaningful test) or `GREEN` (vacuous). Both bad verdicts bounce back to the `test-writer`, max twice. **But red proves the test fails — not that it tests *us***: an assertion that holds because the language, a third-party library, or a mock returning its own configured value behaves as documented goes red before the code exists and green after, exactly like a real test, and nothing downstream can tell them apart — it ships red-verified and reviewed, as suite time plus a false claim of coverage. Only the two sites that *author* it can catch it, so the rule sits at both (`planner` writing the scenario, `test-writer` writing the assertion) as one question: **would this still pass if the production code the task adds were deleted?** The line is whose decision fails the assertion, not whether a framework is in the picture — that our schema requires an email is ours and worth pinning; that the validator rejects a malformed one is theirs. Wiring tasks assert the effect at our boundary instead.
- **Blockers ship with a regression test**: a blocker is a bug the whole suite already ran over and missed, so re-running it after a bare patch proves nothing. Blocker fixes go through a mini-TDD loop (`test-writer` `mode: regression` → `test-runner` `mode: red` → `coder` `mode: fix` → `test-runner`). A blocker that genuinely cannot be pinned by a test returns `NOT-REPRODUCIBLE` and ships with the reason recorded in Zone 2 — never with a faked test. **The test pins the capability, not the finding's prose** — a blocker's wording is written to *locate* the bug, not to enumerate the surface its fix touches, so a test derived from it inherits what the prose omitted; where the fix exposes a set (routes, tools, handlers) every element is covered or the uncovered ones are named. And **a fix that adds a source file has built a layer no `test-plan.md` was written against** — the plan predates it — so a fifth micro-loop step (gate-review caller only, triggered mechanically by an `A` in `git diff --name-status`) loops back once to cover the new module's surface. No red-verification there, deliberately: the code already exists, so `mode: red` would call every passing test vacuous; failures are `new` failures and route to the coder (`docs/field-reports/2026-07-30-fix-pass-layer-untested.md` — 8 tools wired through one wrapper, 1 tested, the `void` one shipped broken).
- **A green suite is not always evidence**: the `reviewer` carries a `test-pass-insufficient` dimension for the bug class a passing suite cannot rule out. Two families: **the code runs but takes a lucky path** (concurrency, shared-resource scoping, ordering, idempotency, resource lifecycle, reversibility of state-mutating artifacts), and **the code never runs at all** (reachability/wiring — a symbol whose only callers are its own tests; a schema or guard verified against fixtures the tests built rather than the real producer's output). Findings there are argued from the code and types; "the tests pass" is not grounds to soften one, and `critique` may not drop one on those grounds — to drop a reachability finding it must **name the production caller**. Test helpers and fixtures are reviewed at production rigour (a broken shared helper makes every test using it vouch for broken code), and code copied from `design.md` gets the same scrutiny as new code.
- **The reachability sweep covers every newly exported symbol**, not just a module that arrived with tests — and the same grep carries two verdicts. Something rested on the symbol (an AC, a plan task, a `$DESIGN` contract) and nothing calls it → **blocker**: the feature isn't in the running system. Nothing rested on it and nothing calls it → **refactor**: dead code, delete it. The second half exists because nothing else in the loop can see it: a linter never calls an *export* unused (it must assume a consumer imports it), and `validate` traces *acceptance criteria*, so a symbol no AC rests on is invisible to both. A package-wide version constant stranded in `error-envelope.ts`, imported by nobody, passed every gate devloop had.
- **One rubric, both delivery paths**: `review` (run) and `pr-review` carry the **same** dimensions — correctness, test-pass-insufficient, impact/blast-radius, risk, design-conformance, placement/cohesion, simplicity (YAGNI/DRY/reuse), consistency — and `pr-review` adds exactly one, test-adequacy, grading blocker/suggestion/nit for a merge decision where `review` grades blocker/refactor. Where a shared dimension is imported by reference, the severity is mapped to the local grammar (`review`'s `refactor` → `pr-review`'s `suggestion`); a mode may never be told to emit a verdict its own output grammar lacks. Risk and blast-radius are not PR questions; they were first written where a human happened to be standing, and `--auto` + `direct` later removed the human from the other path. **The rubric may never be thinner where the humans are fewer** — `direct` delivery merges to `main` with no PR, no CI, and no human, so `review` is the whole gate. Correctness and risk stay separate questions: a faithful, fully-tested implementation of its plan can still leak a secret or skip an authorization check, and no acceptance criterion would notice.
- **Architecture findings are leashed, not invited**: the reviewer raises only what is **falsifiable at a line** — a dead export (one grep), a misplaced symbol (**name the destination file, or it isn't a finding**). Coupling judgments and "encapsulate what varies" are excluded by name: they need judgment about how the system will change, they contradict the YAGNI dimension already in the rubric, and they are the generative kind of finding that would stop `critique` converging (which is also why `critique`'s `NEW` channel bans placement/cohesion outright). If architecture is being missed *systematically*, the levers are the planner's `NEEDS-DESIGN` trigger — a normal feature never runs a design phase, so nobody asks — and the human-driven `architect` conversation, not the reviewer's rubric. Judging architecture after the code exists is the most expensive moment to do it. The banned judgments have a sanctioned home: `/devloop:architect`, pre-code, with the human present — and its accepted ADRs come back to the inner loop as *checkable* constraints (via `context` Zone 1), so downstream conformance never requires the judgment itself to be re-made.
- **The leash only holds if the delegate actually checks** — and for one class it didn't. The reviewer hands coupling and structural judgments to the `designer` "at design time", but the critique rubric scored *interface clarity* (is the interface concrete enough to build against?) and nothing about completeness, so a design could name one side of a declared boundary pattern perfectly and stay silent on the other. **Concrete is not complete**, and a silence trips no conformance check downstream — everything the document says is accurate, so the build invents the missing half, and the cheapest invention is to mirror the half that exists. Closed by making the delegation true rather than by widening the reviewer: `designer` now names **both** surfaces when authoring, and critique scores **interface completeness** as its own criterion (`docs/field-reports/2026-07-25-driving-surface-built-as-driven-ports.md`). Two related positions, deliberately taken: the reviewer is **not** given a "name the first-of-its-kind pattern" finding (that is an observation with no fix — exactly what the leash excludes); instead `review` at **sprint** scope runs one whole-module pass over any module that gained ≥3 files, comparing same-role files to *each other*. That defect is invisible to diff-scoped review by construction — each diff conformed to the design and to its predecessors — so it needs the one instrument in the system that sees across diffs, at the altitude where open judgment belongs.
- **Placement is retrieval, not judgment — and it belongs to the agent that can grep.** Module boundaries are the `designer`'s (`design.md` § Interfaces & data model), but a normal feature never runs a design phase — `NEEDS-DESIGN` fires on a novel subsystem or competing approaches, and *which file does this helper go in* never clears that bar. So on an ordinary issue placement falls to whoever is holding the pen: the `planner`, which opens by disclaiming exactly this ("you do not design the architecture"), fills a `Touches:` field anyway, and **has no `Grep` and no `Glob`** — it cannot list a directory or confirm a path exists. An agent that cannot see the tree, asked for a file, returns a *fluent* one (`src/utils/helpers.ts`), and everything downstream honours it: the coder builds there, and the `reviewer`'s placement finding is refactor-class, droppable by `critique` with one line (unlike reachability, it carries no must-rebut-the-mechanism defense) and **skipped when disputed in auto mode** — so the drift ships and comes back as a refactor issue. Closed by moving the question upstream to the agent that *does* hold `Grep`/`Glob`: `context` writes a **`Where new code goes`** section in Zone 1 — for each kind of thing the ACs add, where this repo already keeps that kind, citing the sibling that establishes it — and the planner **looks up** rather than infers, bouncing `NEEDS-CONTEXT: where a [kind] lives` when a symbol has no entry. No new gate and no new loop: it rides entirely on the existing `NEEDS-CONTEXT` → `deepen` path, for the one class of fact the planner is structurally unable to retrieve. **The `no existing home` row is the load-bearing one** — it is not a failed grep but the signal that a real *decision* exists, and it is what makes the planner write a `Placement:` line (why here rather than beside the nearest relative) instead of guessing silently. That line is the only record distinguishing a placement decision from a lookup; it feeds Zone 2 and gate-plan beat 2, which quotes it and never composes one. **Two limits, stated rather than papered over:** this is precedent-*following*, so it faithfully reproduces an existing layout including its mistakes — improving a layout stays with `architect`/ADRs; and it does not catch a symbol landing in an existing file that is the wrong home *when a plausible sibling already lives there*, since cohesion judgment over existing files still has no owner in the inner loop.
- **Two checks on the plan before anything expensive runs** (`run` gate-plan; both read files already open). **(1)** Every `STANDARD` task has ≥1 `test-plan.md` scenario — the build phase runs the micro-loop *per task*, so a scenario-less task seeds the test-writer with nothing, returns `GREEN`/`RED-SETUP`, bounces twice and halts the run on its smallest item; the alternative, inventing a scenario to fill the slot, puts a test that proves nothing into the suite. It is a **planning** defect, not a rung question: at `STANDARD` a task is a unit of *behavior*, and a thing you cannot write a scenario for is a **step** of the task it serves — fold it in. (Deliberately **not** per-task rungs: that multiplies the licensing-artifact machinery by N for a modest win.) **(2)** No plan task reverses a binding **prohibition** — the *never / must not / cannot* sentences of the ADRs Zone 1 lists, extracted verbatim and put beside the task touching the same surface. A plan that reverses one is a **stop-the-line even in auto mode**, because overriding an ADR is a supersession that belongs to `architect`. This is the only gate positioned to catch it: everything downstream measures conformance against *the plan*, so a contradiction that survives here is never re-examined and arrives at review baked into code, tests and commits that all agree with each other (`docs/field-reports/2026-07-30-green-but-fabricated.md`).
- **A gate the human can't answer is answered `y`** (`run`, human mode only — auto-mode presents no panel at all). The gates were written as status panels: dense, complete, in devloop's own vocabulary, ending in *approve?*. That question has no answer reachable from what the panel shows, so the rational move is yes, and the drift it waves through — a method landing in the wrong file — surfaces later as a refactor issue against a mesh nobody chose. **The fix is an answerable question, not more prose**: length is not comprehension, and a longer wall is skimmed harder. So `STANDARD` gate-plan and gate-design present as **beats, one message each**, every beat ending in something the human can settle from what they just read (*does `validateInvite()` belong in `lib/auth/session.ts`?*), with **"not sure" free** — it expands that beat rather than costing them anything, since a "not sure" that costs more than a "yes" collapses into a yes. Collapsed rungs keep the single panel: pacing a README edit is the same burden in a new costume. **gate-plan beat 2 is the placement gate** — one line per task with its `Touches:` files, a field `plan.md` has always carried (`agents/planner.md`) and the panel always dropped. It marks every new **home**, not merely every new file: a not-yet-existing file (`+ new`) *and* a symbol landing in an existing file Zone 1 didn't name as its home (`+ new home`), because the commonest drift creates no new file at all — a function appended to whichever file was nearest — so a panel flagging only new files asks about the case least likely to be wrong. It is the last moment either is free to move: afterwards moving it is a refactor, and the `reviewer`'s placement finding is leashed to a named destination, so it stays silent on exactly the drift a human recognises on sight. The *why here* line is **quoted from `plan.md`'s `Placement:` field, never composed** — run has no file tree in hand at this gate, and a missing line is reported as missing (it is the planner's to fill). **gate-design is the one gate that loads its artifact** rather than linking it — everywhere else run holds verdicts and leaves the document on disk, but here the document *is* the decision, its silences are never checked again, and a criteria table plus a link asks for approval of something unread. Its beats lead with *what it decides* and *what it commits us to* (**does this interface let the next caller do the wrong thing?** — nothing downstream re-asks), and beat 3 leads with the **gaps**. At gate-review the same principle is one added line, not a beat: **blockers and disputed findings carry a failure scenario** (what breaks, on what input — sourced from the `reviewer`'s explanation, which now must supply it for a blocker or grade it a refactor), because uphold-or-drop is a judgment about cost and a finding written agent-to-agent names only the defect. Upheld refactors and dropped findings stay lists — neither turns on a decision being made here. Every beat is in **the project's words**, never *rung*/*phase_step*/*interface-completeness* — the same boundary `review` holds, restated at each panel write site because the record's vocabulary is the nearest wording at the moment run writes to the human. And a beat names only files, symbols and scenarios that are in `plan.md`/`design.md`/the reviewer's return: a plausible invented one is unfalsifiable at a gate and gets approved on sight. The human may cut the pacing short at any beat ("just go") — same flexibility valve as reshaping.
- **`architect` judges by a fixed method over an open catalog** (`skills/architect/SKILL.md`): a conversational skill acting as a senior architect over a topic, a code path, or an issue. Four layers — *leanings* (an ordered favor profile: SRP as *one reason to change* strongest, then simplicity-by-default, one-way dependencies, explicit-over-clever, composition, consistency, duplication-over-wrong-abstraction — priors, not laws, each stated **with the condition under which it yields**, since a default without one is the dogma layer 1 exists not to be); the *forces method* (**principles never conflict — forces do**: a "principle conflict" is decompressed into the force each side protects and weighed with *local* evidence — git churn, callers, roadmap, blast radius — with deliberation scaled by reversibility, one-way doors being the natural ADR threshold); *tie-breakers* at genuine ties (reversible → simple → boring — where style lives); *precedent* (a question near a recorded ADR must **follow, distinguish, or supersede** it, never silently diverge — so a project reshapes the default taste only through recorded case law, never config). Every recommendation states **both costs** (can't fill both → a preference, not a decision) and lands concretely (destination file/boundary/signature — the reviewer's leash applies here too). Recording is gated by a two-gate **ADR test**, and neither masquerader is ever recorded: **Gate 1** keeps *planning* out of the durable record — a plan (a sequencing / stopgap / "for now" choice, consumed when the work ships; the tell is "we will X") routes to `backlog`/`replan`, never an ADR; only a standing structural constraint ("X lives / points / is bounded thus") does. **Gate 2** is the preference filter (both costs won't fill → dies in the chat). Its **character** negates the generic-LLM-architect failure modes (surveying, hedging, folding): provisional take then verify (facts labeled verified/claimed/needs-proof) — **including its own nouns**, the ones nobody else checks: the concreteness leash is a standing instruction to emit a filename and the fluent filename is plausible rather than real, so every path/symbol/"layer"/ADR number in a map or a verdict resolves against the repo or is stated as new, and an unresolvable one comes out. That check runs **silently** — narrating it ("let me verify", "I confirmed these exist") hands the user a process detail they cannot act on and invites doubt about whatever wasn't narrated; **one verdict**, options-menus banned by name; "leave it alone" is a verdict **with a tripwire** (the observable event that reopens it); patterns are commentary, never the recommendation; uncertainty converts to a spike, not "it depends"; the verdict moves for **evidence only** — an owner override is recorded as an override, never a laundered rationale. That character is **re-enacted on every verdict, not remembered** — the anti-drift guard for a long conversation that would otherwise pull it back to the generic assistant: each landing carries one move, labeled evidence, both costs, a tripwire if deferred, and the **governing ADRs re-checked** — never folding to a merely-pushed preference. Precedent is on that per-verdict list rather than only in the entry scan, because a long conversation drifts into areas the entry scan never covered, and the `Precedent:` field of the ADR template fires at *record* time, downstream of the moment a clash needed catching: the human reads a proposal citing no ADR as one that clashes with none, so a contradiction is offered **as a supersession** or not at all. It **opens** without reciting its method (a short ranked agenda of the load-bearing questions, taken one at a time) and speaks in **simple language with ASCII — never mermaid — shape diagrams**, following the user's language while the record stays the repo's. **Precedence: ADR > `design.md`.** Both bind, but an ADR is project-scoped, human-ratified law and a design is issue-scoped machine output — so the `designer` designs *within* accepted ADRs (checking `.context/decisions/index.md` itself as a backstop behind Zone 1; its critique's consistency criterion does the same) and returns `CONFLICT: ADR-NNN` rather than silently violating one: human mode gates it, auto-mode stops-the-line, because overriding a recorded decision is a supersession and belongs to the architect conversation. The reverse flow is deliberate too — `design.md` boundary decisions never enter the case law by themselves; promotion to project-level precedent happens only through an architect conversation. Where a decision rests on a **fitness function**, the ADR records its **enforcement blind spot** — what the check cannot see and what tool would be needed to see it — because a green check is otherwise read as the decision holding: a rule policed at the wrong altitude passes anything that never reaches its mechanism (a hardcoded constant contains no `process.env` for the lint guarding "configuration is injected" to flag), and a file-level import lint cannot express a symbol-level property at all. In both cases the check passes correctly and proves nothing.
- **An AC is satisfied when it is test-backed *and* reachable — and the trace runs both ways**: `validate` traces every automated AC to a **production call path** (composition root → entry point → the symbol the tests assert against) and records it in Zone 2 — "a passing test covers it" is not sufficient, and was the inference that let a green, fully-tested, uncalled resolver merge with a tick beside its AC (`docs/field-reports/2026-07-13-green-but-unreachable.md`). A forward grep is blind in two directions, so two bounded steps follow it, **one hop each, no further** — *name the producer* (which production code writes each value the AC's assertion rests on; cross-checked against the `test-writer`'s `FIXTURE-BYPASS` lines, because an AC resting on a value a fixture supplied by hand is unverified — `2026-07-30-green-but-fabricated.md`) and *name what comes back* (what the caller receives, and whether anything ever exercised that return — an `N of M` ratio over an exposed surface, not an execution: `2026-07-30-fix-pass-layer-untested.md`, where a write committed and its reply was rejected as malformed). Four failure shapes, all **unmet ACs**: nothing calls it · nothing real feeds it · the reply is unusable · the declared return is unreachable. Human mode blocks with override; auto-mode routes it back to build as one scoped task and **stops-the-line** if the fix needs a decision it isn't entitled to make. Never carried forward as a flag — unlike a manual AC that can't be automated, each is a demonstrable defect. **What the trace proves is bounded and says so**: control reaches the code, the values are production-produced, the way back out is observed — *not* that the value is correct. Claiming more is how a phase that traces arrival gets read as a behavioural check (`2026-07-30-validation-traces-arrival-not-behavior.md`). The traces also feed `review`, which otherwise reconstructs them by hand.
- **`design.md` is part-normative, part-illustrative**: interfaces, signatures, contracts and module boundaries are **binding** (within accepted ADRs — an ADR outranks `design.md`; see the `architect` bullet); **code blocks are sketches** — reasoned about, never run or reviewed. The `planner` must never emit a "copy this verbatim from design.md" task: it converts an unreviewed snippet into shipped code precisely because the document is trusted. The `reviewer` checks conformance against the **binding half only**, and both halves of that matter: code diverging from a sketch is **not** a finding (raising it would make "match the unreviewed snippet" the fix — laundering a design defect into production via a review finding), and code *matching* a sketch earns **no credit** — it is reviewed as fresh code, because "it conforms" was never an answer to "is it correct".
- **`review` verifies; it does not relay.** **The log tells you what was *decided*; only the artifact tells you what is *true*.** Zone 2 is authoritative for history and rationale (and where it is silent, `review` reports the silence rather than filling it) — but for any claim about *behavior* it is a self-report by the system that wrote the code, so `review` goes to the artifact before it vouches: grep the production callers, resolve the commit, read the code, run it. Every other artifact it reads is the inner loop's testimony about itself, and a replay of a self-report cannot catch a self-consistent error — code, test and doc all agreeing with each other and disagreeing with the system (`docs/field-reports/2026-07-13-green-but-unreachable.md`: a resolver shipped green, fully tested, called by nothing).
- **Orientation precedes the change — the human is judging a system, not a diff.** `review` reads **Zone 1** (the facts the run was built against: surrounding code, patterns, constraints) *before* Zone 2, and `.context/decisions/index.md` for any ADR governing the area — project-level law outranking `design.md`, whose *does the shipped code honour it?* nothing downstream of gate-plan re-asks. Zone 1 is the only place the **system** is described rather than the run's history, and reading Zone 2 first is why the opening used to orient the human in devloop's process instead of their project. It feeds a *where this sits* beat that opens the task conversation — what was already here, what this task added — **drawn** (ASCII, `← new`) by default on any multi-file change, since the sketch does that beat's job faster than sentences and leaves the human oriented for everything after it. At sprint scope the picture is drawn **once**, before the per-task walk: eight redraws of the same system is how a walkthrough becomes something to skim.
- **One commissioned-edit mechanism, three consumers** (`skills/tinker/tweak-spec.md`, read by `review` §4.5 and `vibe` §5). **`tinker` was a third consumer and was taken out**: it kept the four roles but diverged on almost every clause — its gate is in the editor rather than the chat, it has no no-behaviour precondition, it picks checks per change, and it never escalates out of the session — so the spec had become mostly one consumer's exceptions, costing every reader context and following none of them. Tinker restates its own variant in `skills/tinker/SKILL.md`. *The skill commissions · the `coder` applies · the human reads the **real diff** · the skill commits.* Extracted into a spec once a third consumer appeared, per the same convention as `plan-spec.md` and `ba-spec.md` — and its negative rules are **restated at each write site** rather than pointed at, because the nearest wording always wins: `$NO_COMMIT` on every invocation (which is what makes the pre-commit scans structurally unskippable rather than merely mandated), the real change read by the human before any commit (`git diff` in the conversation for `review`/`vibe`; in their own editor for `tinker`, with git's file list and the proposed message at the gate), **two coder attempts**, and a discard that restores only the files the coder named — never `git reset`, never a broad `git clean`.
- **The patch: review commissions, it never edits** (`skills/review/SKILL.md` §4.5). A rework that changes **no behavior** — a wrong message, a stale comment, a missing guard — does not earn a new issue plus `replan` plus a full `run`: that run rebuilds from scratch the context and judgment the human is holding at that exact moment. So `review` invokes one `coder` (`mode: express`, **`$NO_COMMIT`**), shows the human the **real `git diff`**, and commits it itself, straight to base — no branch, no PR, two coder attempts maximum, and any escalation trigger (`blocked`/`not-trivial`, checks red twice, a file nobody named, a design question) converts it back into a rework issue rather than pushing through. The **coder never commits here**, because "diff after" is what makes the gate real: a commit made before the human looks turns their "no" into a history rewrite on the base branch. Provenance survives without a GitHub round trip — commit body `Patch of #N`, a Zone 2 entry with `Caught by: human` (so it lands in the retro's Loop calibration like any other detection), and one comment on the issue carrying the SHA. Preconditions are all cheap and all mandatory: no live lock, clean tree, task **shipped** (`[x]`), active sprint only. **`✓accepted` is deliberately not one of them** — it records a verdict, it does not seal the record; *sealing* happens at sprint close, which the active-sprint precondition already guards. Gating on acceptance would exclude the commonest and safest case the mechanism exists for (reviewing a sprint in order, every earlier issue is accepted by the time you reach the last), and its realistic alternatives — override the gate, file an issue nobody schedules, or say nothing — are all worse. A patch may touch a file owned by **another issue in the same sprint**: Zone 2 on the issue under review, GitHub comment on the issue owning the code. **This is not a thinner gate than the inner loop's** — that machinery substitutes for an *absent* human, and here one is present reading the actual diff, which is strictly more oversight than `run --auto --direct` gives an ordinary task. **The present human is the whole justification**, which is exactly why the commissioned edit exists only where there is one — `review`, `tinker`, `vibe` — and why no autonomous path may ever reach for it: remove the human and nothing is left holding the gate. The difference between the three is *scope*, not rigour: `review` and `vibe` patch **one** no-behaviour thing found mid-conversation, while `tinker` is a working session of any size and therefore adds what building needs (its own branch, a test when behaviour changes, `run`'s planner/designer front half when an instruction needs a plan, and an independent verdict plus a review pass before it merges). Six things in a review — or one that changes behaviour — are a hand-off to `tinker`, not trips through this gate.
- **Its instruments, cheapest first**: **grep the callers** (an AC whose symbol is called only by its own test is satisfied as a library function and unsatisfied as a behavior — a finding, for one command); **`git log <merge-commit>..HEAD`** (did a later task undo this one); **walk the change** (the shipped code in *reading* order — entry point → seam → new code → what changed for the caller — anchored on one concrete input where there is a flow to follow, since a journey is easier to hold than a tour of files; one claim per step, each with a narrow citation, drawn as a call path, **labeled read-not-run** because a walked journey and an observed one are indistinguishable on the page; it also does the reachability check for free wherever a hop has no production caller. The pair to *walk the build*, which is how it came to exist rather than what it does — led with on a ⚠ or new-structure task, offered otherwise); **the demo — which the human runs, not review**. A task marked done means green tests and each AC traced to a call path, but that trace is *static*: it proves the code is reached, not that the behavior out here is right, so somebody still has to run the composed system through its **real entry point** (never the module the task built, which always works and proves nothing). Review running it and reporting "✓ works" is a self-report about a self-report — the replay problem one level up, leaving the human trusting a paragraph. So review hands over a **recipe** (exact steps, real values, *what should happen* **and** what wrong looks like — without the second line they only see what they were told to look for, plus the line that makes it happen), **verifies the recipe's ingredients resolve but never performs its scenario** (a step-2 404 wastes the human's time and teaches them to skip the next one), then asks what they saw and takes that as the result. AI-run **probing** survives only for a *specific hypothesis* from reading the code — one command to falsify beats sending the human on an errand; a probe is for **finding** something, the recipe is for the human to **believe** it, and swapping them reproduces the reassuring paragraph the split exists to kill. Offered only where the task changed something observable ("nothing to try here — it's internal" otherwise). The never-fabricate rule bites hardest here because a recipe's *shape* looks like output: *what should happen* is a **prediction**, future-tense, derived from a cited line — rendered as a transcript it is a fabricated demo. If it can't be run at all, `review` says why and offers *walk the change* as the read-only substitute. A recipe that comes back wrong — or a behavior that never shows at the entry point — is a **defect found, not a failed demo**: `Caught by: demo`, the gate being the demo whether the human ran it or a probe did (the retro's `human` row is for what they caught by *reading or asking*, no run involved). Every one of those **replays or verifies what was built**, so one more **questions** it: **interrogate the design** — who is the next caller, and does this interface let them do the wrong thing safely; is any declared return unreachable; does an architecture comment match the import graph. Offered on any task that set new structure, always on a security-relevant seam, and **led with the code rather than a conclusion**, because the human is the sharpest instrument here (of nine findings in the review that produced it, four began as their unprompted question and two more from checking those).
- **An empty flag list is not evidence of quality.** Everything `review`'s opening surfaces — blockers, `NOT-REPRODUCIBLE`, baselined failures, 3-attempt tasks, critique catches — is the run's **self-report** of what it found *hard*. Difficulty is not defect probability, and a task that was confidently wrong reports clean: it executed a flawed specification flawlessly, first try, all green. So `review` never calls a task clean on an empty list alone; it spends one pass on what no gate can flag — the **acceptance criteria themselves** (an AC the loop satisfied perfectly can *be* the defect: one mandated returning only a role, leaving the next issue no safe way to know who was invited — an account-takeover path shipped with a green tick beside the criterion requiring it), **first-of-its-kind structure** (it becomes the exemplar handed to every later issue), and **architecture claims in comments** (in an agentic loop a false one is an instruction to the next agent, not stale prose). Saying the list is empty and saying what you checked yourself are two different statements; the human needs both (`docs/field-reports/2026-07-20-clean-record-nine-findings.md`).
- **Two timeframes**: merge-as-you-go means the tree holds later issues too. *What did this task ship?* → its merge commit + `refs/devloop/issue-N`, frozen. *Is it still true?* → `HEAD`, and anything you run. Divergence between them is its own defect class — a later task bypassing an earlier one's guardrail, which **no inner-loop gate can see** (`#46`'s reviewer reads `#46`'s diff, not `#43`'s ACs; `#43`'s tests still pass because its code still *works*, it has merely stopped being *called*). The rework is then raised against the issue that **caused** it, never the one it broke. **The journal is what makes that attribution possible at all** — `git log` says a later commit touched these files and stops there, and once `tinker` exists a hand-tuned value and a regression are indistinguishable in it. So `review` asks the journal *why*: `run #46 · shipped` → a real defect, rework against `#46`; `tinker · hand-tuned` with its reason → somebody watched the app and changed it on purpose. Without that line the safe-looking call — *"something changed this, raise it"* — files a rework against a deliberate human decision.
- **`review` is a conversation, not a procedure**: the skill specifies the *sources*, the *instruments* (demo · walk the build · interrogate the design · explain an artifact · show the failure · dig into a flag · verdict), and the few rules that don't bend — the model chooses which fit the task. Over-scripting a conversational skill buries the load-bearing constraints in choreography. The **sprint close ceremony** (reconcile → retro → tag → close milestone) stays procedural: irreversible outward-facing writes in a format other things read.
- **`review` speaks the project's language, not devloop's** (`skills/review/SKILL.md` *How to speak here*): its human is the **product owner**, judging *what* shipped — rungs, phases, agent names, Zone 2, `NOT-REPRODUCIBLE`, `Caught by:` are this codebase's vocabulary for *how*, and every one of them is translated at the boundary ("the blocker shipped `NOT-REPRODUCIBLE`" → "we fixed the bug, but no test proves it stays fixed"). The leak is structural rather than stylistic, which is why the rule is restated at each site that emits user-facing text rather than stated once: `review`'s whole job is reading devloop's internal record aloud, so the record's vocabulary is the *nearest* wording at exactly the moment the model writes to the human — the sprint-snapshot ⚠ cells and *walk the build* are where it hits hardest. The one exception is where the loop **is** the subject (process feedback, the retro's Loop calibration) — named plainly there, glossed in place. Register is load-bearing here, not politeness: an explanation the product owner must decode before they can tell whether their project is in trouble doesn't do the outer loop's job, and the human whose attention this skill exists to point is the one person in the loop who never agreed to learn its internals.
- **The conversational skills share one talking contract: ground first, draw first, one thing per message** (`skills/review/SKILL.md` *How to speak here*, `skills/architect/SKILL.md` *How you talk*). Both skills open holding a model of the system that the human does not have — `review` has just read Zone 1, the timeline and the diff; `architect` has just read the code — and a reply written from inside that model is accurate, complete, and unfollowable. The human cannot say so without admitting they lost the thread, so they say "ok", and the verdict or approval that comes back was never really theirs. Three rules, restated at every site that writes to the human rather than stated once: **(1) ground before judgment** — no file, symbol or concept may appear in a judgment before it has appeared in one plain line saying what it is and does, in the project's words, *including the pieces that were already there*, because the human is being asked to judge a change to a system, not a diagram of boxes; the same treatment applies to the model's own analysis vocabulary (*unreachable*, *seam*, *entry point*, *coupling*, *blast radius*), where the plain sentence leads and the technical label follows it or is dropped — both skills carry a translation table, `review`'s alongside its existing devloop-vocabulary one. **(2) draw first, then describe** — a structure written as prose has to be reassembled in the reader's head; ASCII (never mermaid), every node real and glossed, and *before* the paragraph, since a picture arriving after the explanation is decoration while the same picture in front of it is what lets the explanation be short. **(3) one thing per message** — a budget of one picture or ~8 lines ending in something answerable, because a message carrying a claim plus its implications plus the next step forces the human to choose what to answer before they can answer at all. The check-in question is the load-bearing half of (3) and is the same shape as `run`'s gates: *"does that match how you thought it worked?"* is answerable from what they just read; *"shall I continue?"* has no answer but yes, so it collects a yes and measures nothing — and "I'm lost" is made explicitly free, since a user who cannot cheaply say it keeps nodding and every later answer, acceptance included, is worth less than it looks. In `architect` the contract is named as the **third** fixed thing beside the way of deciding and the way of behaving, and one line of it is added to the per-verdict shape re-enacted at turn 50 as at turn 1 — the talking rules drift first and most invisibly, because nothing in the conversation objects when a verdict stops being followable.
- **Git history survives the squash**: `run` squash-merges and deletes the branch, so the coder's per-task commits (cited by SHA in Zone 2) would become unreachable. Before deleting, `run` archives the branch tip at `refs/devloop/issue-N` (a custom ref — a gc root that doesn't clutter `git branch`/`git tag -l`; **local, never pushed**) and records `merge-commit:` + `history-ref:` in the state file. `review` anchors the task's diff to the exact merge SHA rather than grepping `$base` for `Closes #N` (which matches `#4` inside `#42`), and cites a ref only after it resolves.
- **Detection provenance**: any Zone 2 entry recording a defect carries **`Caught by:`** (`test-red` · `typecheck` · `lint` · `reviewer` · `critique` · `validation` · `spike` · `demo` · `human`; the last two are written by `review` in the outer loop). Raw evidence (failing output, stacks) goes to `work/issue-N/logs/` and is cited under **Artifacts** — never pasted into Zone 2, which every downstream agent loads. This is what lets `review` replay *how* a bug was found instead of guessing, and what fills the sprint retro's **Loop calibration** table (which gates actually fire, and which never do).
- **Lock discipline**: `run` writes `.lock` on start, deletes it on clean exit, at `pending-review`, and at `merge`. Stale lock (dead PID) is auto-cleared with a warning. `tinker` and `vibe` hold the same lock (`holder: tinker` / `vibe`), so no two altitudes ever write one tree.

- **The journal is the only cross-run memory, and before it there was none** (`skills/tinker/journal-spec.md`, `.context/devloop-journal.md`). There is exactly **one** channel by which past work reaches a future run's agents: the `context` agent assembling Zone 1. What it could retrieve was GitHub issues, the code, and `decisions/index.md` — so an issue's Zone 2 timeline, a sprint retrospective, a vibe manifest and every hand-tuned value were **written once and read by nothing**, and sprint 4 rediscovered what sprint 2 learned. The failure this makes concrete: a value a human tuned while watching the running app is, to the next agent that opens the file, indistinguishable from a number somebody typed carelessly — and the cheapest thing in the world is to clean it up. The journal is deliberately the **same shape** as the ADR index, the one retrieval surface here that already works: **a small index scanned every time, pointing at big records pulled rarely.** Five fields — `date · mode · outcome · areas · what-and-why → record`. Three of them are load-bearing in a way that is easy to get wrong. **Outcome is a closed set** (`shipped` · `blocked` · `abandoned` · `hand-tuned` · `decided` · `superseded` · `closed`) because a word outside it cannot be matched on, and *somebody already tried this and it did not work* is the most expensive fact in a project to rediscover and the cheapest to record. **Areas are derived mechanically** — `git diff --name-only` collapsed to globs, never composed: a fluent, plausible, wrong area poisons retrieval for every future run and fails the way a guessed MCP tool name fails, silently and with confident output. **The `why` is the half that matters** — `toast 2s→4s` is a changelog and git already has one; `toast 2s→4s (owner watched it, 2s too fast to read)` is the entire reason the file exists. Appended with `cat >>`, never `Edit`, for Zone 2's reason; **never rewritten** — a correction is a new line, because history that gets edited is not evidence. The `context` agent selects entries whose areas intersect the work, caps at ~5, and emits them under Zone 1's **`What happened here before`** — **provenance, not history**. And it is emitted under its own heading, never under `Constraints`: **an ADR is law, checked at `gate-plan`; a journal fact only makes the next agent aware.** That asymmetry is stated rather than papered over, because claiming a journal line binds anything would be the same error as reading a green check as proof a decision is holding. Where something genuinely should bind, the escalation is `architect` and an ADR — which is why `tinker` offers exactly that when the journal shows the same area tuned three times.

- **`docs` is the standing description — devloop's only semantic memory, and the only thing it writes for humans to read** (`skills/docs/SKILL.md`, `skills/docs/docs-spec.md`). Everything else devloop records is **transactional**: the journal is anchored to an episode, Zone 2 to an issue, an ADR to a decision, a sprint review to a sprint, `design.md` to one issue and superseded by the next. None of them answers *what is this system, right now*, and you cannot reconstruct it by reading all of them because they are **additive** — knowing the present state would mean replaying every episode and applying the deltas in your head. The AI never notices, because the `context` agent rebuilds a task-shaped slice of that answer from scratch on every issue and throws it away; **a human cannot, and that asymmetry is the drift** — after six sprints the humans reason about a system that no longer exists and a new developer has nothing to join. So: the journal is episodic memory, the ADR index is law, this tree is the standing description. The load-bearing positions:
  - **The doc tree's real enemy is staleness, and a stale human doc is worse than none** — the reader trusts it, and by this repo's own rule a false architecture claim in an agentic loop is an *instruction to the next agent*, not stale prose. Three mechanisms, all borrowed: every claim is **falsifiable at a line** (the reviewer's leash applied to prose — a sentence that cannot carry a `path:symbol` citation either cites the record or comes out); each node records the **commit it was written against** (`Based-on: <sha>`), so *is this stale?* is `git diff --name-only <sha>..HEAD -- <covers>` rather than a judgment; and the audit is the **default** invocation, because a drift check reachable only by regenerating the world is a drift check nobody runs.
  - **The cursor is a SHA, not a date, and that is the whole difference between working and decorative.** A date cursor against the journal sees only devloop episodes — a hand fix on `main`, a teammate's merge, a dependency bump, anyone on the team not running devloop is **invisible** to it, and those are exactly the changes a growing team accumulates. The journal is the *annotation* on the diff (it supplies the *why* for the commits git found), never the source of truth. The SHA also turns *is this document still true?* from an unbounded re-read into a **bounded diff** — the same "a diff range is a parameter, not an inference" rule, applied to prose — and makes a refresh non-destructive (update against the diff; a from-scratch rewrite destroys every good sentence a human wrote, which matters most on an `Origin: adopted` file that was somebody's work).
  - **Structure and behaviour come from the code; intent and rationale come from the record — and where they disagree, that is the most valuable output.** A tree written from ADRs and sprint files describes the system somebody *intended* to build (`review`'s rule: the log says what was decided, only the artifact says what is true). So the audit reports *ADR-007 confines DB access to `api/`; `workers/sync.ts:31` imports the client directly* — the one check nothing else in devloop performs: the `reviewer` sees one diff, `gate-plan` checks a plan against prohibitions *before the code exists*, and **nobody ever re-asks whether the standing law still describes the standing code.** Leashed exactly as the reviewer is: falsifiable at a line, never a judgment about whether the rule is still good. And findings **route, never resolve** — doc wrong → refresh · code wrong → `backlog` · rule wrong → `architect`. Silently rewriting a document to match code that violates an ADR launders an architectural drift into a documentation update, and the record then agrees with the defect.
  - **The map is a decision; the documents are output.** A freely-reasoned tree is not stable across refreshes — run it in sprint 3 and get `backend/`, run it in sprint 7 and get `services/` — so links rot, bookmarks die, and nobody can tell what changed about the *system* from what changed about the model's taste. So `.context/docs-map.md` is derived once with the human, then **amended, never re-derived** (the same treatment as `vibe.md`'s plan), while contents regenerate freely against it. Structure is reasoned per project — real systems differ, and a hardcoded doc set does not survive a monorepo — but **every node corresponds to something real in the repo**, a node exists only if it can state a **Reader** and a **Question** and has real content today, and the descent stops where the next level would describe things that change every sprint (the surveyor's churn numbers are the evidence, not a guess). That stop rule is also why there is no API reference and no class diagram: they sit below the line, and neither has to be banned by name.
  - **Never pad a node.** There is deliberately **no floor** — two documents is a legitimate map, and a small project honestly surveyed gets a small tree. A `development.md` reading *follow the existing style* teaches the reader that this tree is filler and they stop reading the ones that are not; one empty document costs the credibility of all of them. The skill therefore **says the size out loud and why**, because someone who asked for comprehensive documentation and receives two files will otherwise think it failed.
  - **`docs/architecture.md` has a fixed skeleton, deliberately unlike the tree** — six sections, same questions, same order, in every project, because a per-project *orientation* shape defeats orientation. Two of them carry weight nothing else does: **§2's box→directory table is the load-bearing half, not the picture** (a diagram whose boxes bind to nothing reads as authoritative and ages invisibly; with the table every box is falsifiable by one glob, and those globs are what the child nodes' `Covers:` are built from), and **§4 names what actually *enforces* each rule** — the ADR **enforcement blind spot** surfaced where a developer meets it, since right now they learn which rules are real by having a PR rejected, and *"convention only — caught in review or not at all"* is a different and more useful fact than both "enforced" and "no such rule". §3 traces **one thing happening end to end** (`review`'s *walk the change* pointed at the system; the flow the brief's scenario names, three the hard cap) and ends with **`Proved by <test>`** where one exists — a walked journey and an observed one are indistinguishable on the page, so the citation is what converts a reading into evidence, and its **absence** then sits in the most-read file in the repo.
  - **`Written:` and `Confirmed:` are separate fields, and `Confirmed: —` is the honest common case.** Nobody is going to read forty generated leaf documents, and a single `verified` field would quietly claim they did — this is the `AUTO-APPROVED — NO HUMAN REVIEW` marker in a second costume. But the docs themselves are **not** stamped: forty banners is zero banners, and it is unactionable for the one person it warns. The honest statement goes **once**, in the entry document, and `Confirmed:` earns its keep in the audit, where **unconfirmed ∧ stale** ranks above either alone. For the same reason the audit **writes nothing** — not the map, not a `Confirmed:` line: citations resolving is not the same as a document being true, and an audit that could stamp freshness would make *verified* mean *the greps still hit*, which is the green-check-as-proof error exactly.
  - **Three agents, and the audit is deliberately not one of them.** `surveyor` (read-only; `map` derives structure from what *runs*, `component` digs one node and traces one journey) exists on economics — the largest input in the skill, the smallest return. `doc-writer` writes **leaves only**, commissioned per `skills/tinker/tweak-spec.md` (*the skill commissions · the agent writes · the human reads the real diff · the skill commits*), and has **no `Bash`**, so "cannot commit" is structural rather than instructed. `doc-critic` is `ba-critic`'s twin with one different question — *could a new developer read this and still not act?* — a **fresh instance per document**, and it is **handed** the citation-resolution results rather than computing them, because a reasoning layer over grep output is precisely where fabrication enters. The map and `architecture.md` are never delegated: those are what the human is in conversation about, and a re-invoked agent shares no memory with the previous call. The audit stays in the skill because its checks are set intersection and grep, and its output has to become a conversation.
  - **The tone contract is enforced, not suggested** (`docs-spec.md`). These documents inherit the conversational skills' talking contract moved from speech to page, and the problem is worse there: a writer holding a full model of the system produces prose that is accurate, complete and unfollowable, and unlike a conversation the reader cannot even say "ok". One idea per paragraph, four sentences maximum · **draw first, then describe** · ground before judgment, *including the parts that were already there* · plain sentence first and the technical label second or dropped · **no hedging** (a hedge in a document about one specific codebase means the writer did not check — it is a signal to go look, not a way to finish the sentence) · every claim cited inline. A style note is applied on document 1 and forgotten by document 23, so `doc-critic` grades tone as a **finding class** — a wall of prose is exactly its question.
  - **Mermaid here, ASCII in conversation** — a deliberate split from `architect`, which bans mermaid because an unrendered block is unreadable in a terminal. A document file is viewed rendered, diffs as text, and survives editing. Different medium, different call.
  - **`docs` never takes the lock**, because it never writes source and so cannot conflict with anyone's content; the only shared resource is the commit, guarded at the commit by the tweak-spec preconditions (no live lock, the real diff shown) plus **staging only the paths it wrote, by name** — never `git add -A`, since the tree may hold somebody else's work. Holding a lock for the length of a documentation conversation would block real work for no gain.
  - **The journal line's areas are the *covered code*, not the documents** — the union of the touched nodes' `Covers:` globs, copied verbatim from the map. Still mechanical rather than composed, and it is the point: a future agent working in `src/auth/**` gets told a document describes this area, whereas areas of `docs/**` would intersect nothing and be retrieved by nobody.
- **`tinker` is the tight loop — anchored to the running system, not to a plan** (`skills/tinker/SKILL.md`, optional goal argument, session-driven, runs in **both** tracks — it detects `vibe.md` vs. `master-plan.md` and picks its register, no flag). The human gives instructions (*change this, now try it, commit*) with the app in front of them; the AI's job is **do what they said, and don't let the project drift while doing it.** **The skill must stand alone — this file is not deployed.** At ~980 lines the skill had grown long enough that its rules risked being skimmed, so it was compacted to imperatives, each keeping the one-clause *because* the running model needs to apply it at an edge (why `$ACCEPTED` travels to every suite-runner, why the review range is passed, why the coder's green is not the verdict, why absolute paths), with the negative rules restated at each write site. The history and field-report reasoning below is for maintainers; anything the model needs to decide correctly lives in the skill, never only here. The load-bearing positions:
  - **The rung question is asked per instruction, and stated out loud.** *Does this add or alter behaviour — and if not, does it touch any checkable surface?* Same four-way call the `planner` makes for an issue, same one-way ratchet, but the human can overrule it in two seconds — which is the right gate here, because unlike `run`'s panels this is a question a developer *can* answer instantly. tinker needs no new classification machinery, and deliberately gets none.
  - **Change behaviour, expect red.** When the call is *test first*, new behaviour goes through the real micro-loop (`test-writer` → `test-runner` `mode: red` → `coder`); **changed** behaviour means an existing test now encodes the old expectation, so the work is to find it and update it, red-verified. And the diagnostic that makes the loop worth running: **a suite that stays green after a behaviour change is a question, not a pass** — either nothing covered it (write the test, or take the override deliberately), or something should have failed and the change never took effect (a defect, free), or a test covered it too loosely to notice (a weak test, a real finding). Never let a silent green stand in for proof. **Whether a test exists at all is decided per change, in order, first fit wins**: a tuned value or look/wording (the only assertion restates the value) → none; an existing test pins the old behaviour → update it, red-verified; new behaviour our code decides → write one; behaviour a library decides → assert at our boundary, or none with whose-decision-it-is recorded; nothing the profile can run reaches it → cannot test first, said out loud (set up testing, or override); more than one scenario → planned path. A direct change has no `test-plan.md` and gets none — tinker writes the one scenario itself (it holds the context and `Grep`), vets it with the planner's *would it still pass if the code were deleted?*, states it in the clause that announces the call, and passes it inline as the `test-writer`'s `$SCENARIOS`; the `coder` takes an inline `$TASK` in `implement`/`express` for the same reason. Both agents' contracts previously required plan files, so the direct test-first path as first written could not run at all.
  - **Proof is only deferred by an explicit override, and the override is what gets written down.** This is where tinker parts from `vibe`: vibe defers by default because it has no suite, tinker has one, so the ledger (`devloop-unproven.md`) records only the times a human said *"not now"*. That keeps the ratchet intact and the file short — and an override is recorded **as an override**, never laundered into a rationale, exactly as `architect` treats one.
  - **An ADR conflict is a raise, not a stop.** In `run` it stop-the-lines even in auto mode, because a supersession belongs to `architect`. Here a human is present, so tinker quotes the prohibition, offers *one-off / architect / drop it*, and on a one-off records the override and carries it to the close report.
  - **The human is the oracle; probes are the AI's.** They reload the page and say what they saw; tinker never reports that it works. A **probe** — one command against `logs`/`db-console` to settle a *specific hypothesis* from reading the code — is tinker's, shown as typed and as printed. *A probe is for finding something; their observation is what makes it true*, and swapping them produces the reassuring paragraph the split exists to kill (`review` §4's rule, at a faster cadence).
  - **The gate is in the editor, not the chat, and it always stops.** After the checks pass, tinker shows a one-to-three-line summary, the file list **from `git status --porcelain`** (never composed — it is what catches a file nobody named), and the proposed commit message, then waits; the human reads the change in their own IDE and tries it in the app, and only an explicit *commit* commits. A diff pasted into the chat was the wrong medium for a developer at a keyboard with the IDE open — and the first version, whose own example printed a SHA *before* "reload and tell me", taught the model to commit first and ask afterwards, which is the one thing the commissioned edit exists to prevent. Two consequences: a correction before the commit is a **retry** of the pending change (tuning a value is not a failed coder attempt), and because the human may edit in the IDE, the change is **fingerprinted at the gate and re-checked on the yes** — if it moved, the checks re-run before anything commits. `review` and `vibe` keep the diff in the conversation (`tweak-spec.md`).
  - **One tweak, one commit** — not ceremony: after three tweaks and *"it's still wrong"*, it is the only thing that makes the revert precise. On a session branch, merged **without squashing** at close, deliberately unlike `run` (there the plan is the record and the commits are scaffolding; here it is the other way round).
  - **Checks are chosen per change; close owes all of them.** A behaviour change (test-first or planned) runs every profile check before its gate. A no-behaviour change — look and wording (unless a test already pins the old value), a tuned constant — runs only the **quick checks that can see the touched files**, judged from what the profile actually lists (what each command reads, whether it is a static pass or runs the suite/build/browser), **never from a hardcoded list of names**; nothing qualifying means nothing runs, and the gate says so. A project that never set up such a check does not get one invented. This relaxes `run`'s "every rung runs its full check set" deliberately and only here, because tinker has a later gate to defer to that `run` lacks: the session branch is private, close runs every check before merge, and one commit per change keeps a close-time failure a short search.
  - **Three gates the tight cadence cannot supply itself, all at close**: **every** profile check — tinker runs the non-test commands itself and the `test-runner` re-runs the suites (`unit`, then `full` for end-to-end) as the verdict, since `test-runner` runs only test commands and its `full` mode means end-to-end, not "everything" (the first wording asked it for a job outside its contract); an **ADR check** — every ADR governing an area in `git diff --name-only $BASE...HEAD` (not only those in Zone 1), its prohibitions put beside the session diff, a violation falsifiable at a line; and a `reviewer` pass over `$BASE...$HEAD` — the only instrument that sees the session whole: design conformance, placement, unreferenced exports, risk, blast radius. The human upholds or drops each blocker; an upheld one ships with a regression test, before the merge.
  - **The goal is where, never what.** `/devloop:tinker I want to refactor the sign-in page` — the text after the command names the session and seeds Zone 1 for that area at open (ADRs, where code goes, the journal), followed by a four-line orientation built only from what was retrieved. It never starts work: the first instruction says what to change.
  - **Size scales the process, never the answer.** The first version carried a "bigger than a tweak" raise, an escalation row routing new modules/migrations/dependencies to `replan`, and a ~10-tweak/15-file session budget — so in use it told a developer their feature was out of scope and should be an issue. That misread the skill: tinker is the collaboration, under human control at every step, and what protects the architecture is **process, not smallness**. So step 0 of every instruction sizes it: **direct** (one behaviour, every file nameable now) runs the per-instruction cycle; **planned** (several behaviours, unnameable files, a new module/layer, more than one way to build it) runs `run`'s front half in the session — the instruction and its acceptance written into Zone 1, the `planner` (NEEDS-CONTEXT filled by tinker itself, since it holds `Grep`/`Glob`), a `designer` pass + fresh critique + a design gate on `NEEDS-DESIGN`, `run`'s two gate-plan checks (scenario per `STANDARD` task, no ADR prohibition reversed), then the plan **stops for the human only when it holds a decision that is theirs and costs a rebuild to change** (a new home, a dependency or migration, a security seam, thin coverage, a departure from the design) — otherwise one line saying what is being built, and building starts; the tasks run with no gate between them and nothing committed; then `run`'s QA on the whole instruction (an independent `test-runner` verdict on the suites, each acceptance line traced to a production caller) and **one** § 6 gate and **one** commit for the instruction. The `reviewer` does not run per instruction: it reads a committed range, and close is where the human expects the heavy pass. A dependency or migration is a raise (name the undo cost, get a yes), not a stop; nothing routes work to `backlog`/`replan` unless the human asks. The journal outcome follows: `shipped` when the session carried a planned instruction, `hand-tuned` when every change was direct — the next agent should treat designed code and a hand-tuned value differently.
  - **Zone 1 is seeded from the goal, then extended per instruction** — `run` builds it up front because it knows the issue; tinker knows only the goal's area at open, so it retrieves for that then, and again the first time an instruction touches an area Zone 1 does not cover. And it does its **own** placement lookup rather than bouncing `NEEDS-CONTEXT`: unlike the `planner`, tinker holds `Grep` and `Glob`, so a fluent guessed path is inexcusable here.

- **`vibe` is a separate track, not `run` with the tests turned off** (`skills/vibe/SKILL.md`, no flags, state-driven — bare invocation resumes; free text is read as intent). It builds a **small greenfield app with a non-technical owner present**, and three things make it a track rather than a flag on `run`: the **rung ratchet fights you** (vibe tasks add new behavior, so an `EXPRESS`-pinned run fails its triviality proof and auto-bumps straight back to `STANDARD` — TDD; the ratchet has no hole and shouldn't grow one), **GitHub is load-bearing in `run`'s spine** (S4 resolves an issue, labels select the workflow, `Closes #N` closes it — and the target user has no repo), and **`run`'s gates speak devloop**. Git *is* required: it is the undo button. It borrows the agents unchanged except one added `coder` mode, so the dangerous parts stay shared and get fixed once. The load-bearing positions:
  - **"No TDD" is not the position — "proof deferred and written down" is.** Every task that ships untested adds a row to the **What we haven't proved yet** ledger in `vibe.md`: what it made possible, and what would demonstrate it. Without the ledger, *we'll test it at the end* becomes *we never tested it*, and the harden pass would have to reconstruct what matters by reading all the code — which reliably produces coverage of whatever was easiest to cover.
  - **The demo recipe *is* the deferred test specification.** `review` §4's *what should happen* is already a prediction in the user's language derived from a cited line — that is an assertion. So harden writes e2e tests **straight from the recipes** and unit/integration tests from the seams they cross. One artifact, two consumers, no extra authoring, and the suite ends up proving *what the owner was actually shown* rather than what was convenient. Post-hoc tests can't be red-verified (the code already exists — the same reason `run`'s fix-pass fifth step skips `mode: red`), so the 3–5 recipe-derived tests get a **vacuity spot-check** instead: break the production line, confirm the test fails, restore.
  - **The plan is a sequence of demos, not a sequence of tasks.** *A gate the human can't answer is answered `y`* applies hardest here: "approve these twelve tasks?" is unanswerable by a non-technical person, so it collects a yes and measures nothing. Milestones are named by what the owner will *see*; tasks live underneath as detail. **Milestone 1 is always "it runs on your computer"** — it front-loads the environment problems that otherwise surface at milestone 4 and get blamed on a feature. Each milestone cites the brief line it `Delivers:`, a two-way trace where both directions catch something: a milestone citing nothing is scope creep, a brief line nothing cites is a promise nobody is keeping.
  - **An iteration ends at a demo point, never mid-milestone** — otherwise the owner has nothing to look at, which is the entire premise. Each demo point is a real `git tag` (`vibe-demo-N`, not a hidden ref) precisely so the owner can be *told* the undo exists.
  - **Ask the product question; announce the technical answer.** Asking a non-technical person "SQLite or Postgres?" is the sin — but *not* asking "will two people use this at once?" is also a failure: that is the product question that actually decides the database. Four beats: question → decision → why → **can we change it later**. That last one is the most useful thing anyone can tell a non-technical person about a technical decision, and nobody does: a decision presented without its reversibility reads as permanent, so they agonise over cheap choices and wave through the one-way doors. There is a **decision budget** — five standing questions, everything else decided silently and recorded — because the alternative is a five-minute conversation becoming forty.
  - **Security splits by reversibility, not severity.** A committed credential cannot be patched out of history, so a cheap mechanical **secret scan runs on every diff before every commit**; everything else (exposed internals, a missing authorization check) is fixable and waits for the `reviewer` at the demo point. The scan is structurally unskippable rather than merely mandated: `coder` is invoked with **`$NO_COMMIT` on every task**, so nothing can reach a commit without passing through the skill — which also solves the commit-message problem, since there is no issue number to reference and the behavior is the durable thing.
  - **Fake data has no home here, so it defaults into the shipped source.** Everywhere else the test tree holds it and the `test-writer` owns it; vibe has no test tree during the build, the demo needs data, and the only place left is production code — where nothing downstream catches it, since a fixture the app *imports* is called (so reachability reads it as live) and works (so the checks pass). Three rules, preference-ordered: **prefer no fake data** (the strongest demo is the one where they type it in through the real entry point — seed data is only for what they *cannot* create yet); **one directory outside the app**, looked up not composed, loaded by its own command, named in Zone 1 from milestone 1 so it is never invented under pressure wherever the coder happened to be working; and **the boundary is grepped before every commit**, in the secret scan's position and for its reason — cheap to detect mechanically, invisible to every later gate. A fake **behavior** is a different object and is tracked separately in **Standing in for the real thing**, never in the ledger: a sign-in that accepts anything demos as a working feature and the recipe's *what you should see* is perfectly true, so the defect is that they watch it work and it does not work. It is named out loud at the demo and **blocks the share exactly as an uncovered ledger row does**; filing it as *unproven* instead would record something untrue about what the app does, and hardening would then try to write a test for it.
  - **Two languages, recorded once, because neither is derivable here.** Everywhere else in devloop the rule is *follow the user, write the repo's language* — which needs a repo whose language you can read off existing code (vibe *creates* the repo) and a human who can read both (this one may not). So the manifest holds two independent fields: **`Talking:`** governs the conversation and everything written for the owner (the brief, the manifest entire, ledger and stand-in rows, demo recipes, the Log), **`Writing:`** governs everything written for a machine or a future developer (source, identifiers, commit subjects, the journal, Zone 1/2). Read at startup **before the first word**, and the **recorded value outranks the language of the message in front of you** — one "ok go" in English must not turn the project English; a switch is asked for, never drifted into. `Writing:` is settled in § Decisions as an ordinary decision — *announced, not asked*, since the talking language is already observable and the code's language is a technical answer whose reversibility (close to a one-way door) is the one thing on that list a non-technical person can weigh unaided; it therefore costs nothing from the five-question budget. **The load-bearing consequence is the nouns**: `ba-spec`'s domain nouns become the code's vocabulary, so when the two languages differ each noun must be *translated*, and a translation made silently is made again differently on the next task (`congViec`, then `task`, then `job` — one thing, three names, a forked domain model). One mapping, recorded in the brief's *Words we're using* as an identifier column with `⚑` on every translation the model chose, copied by every reader and never re-derived — and **where the writing language has no clean word, keep theirs**: substituting the nearest available word does not rename a thing, it changes what the thing is. `tinker` reads both fields from the manifest it already opens to pick its register. Deliberately **not** generalised to the full loop, whose humans are developers and whose writing language is readable straight off the code; if it ever must bind there, the promotion path that already exists (a vibe Decision → an `architect` ADR) is the route, and nothing new is built for it now.
  - **The plan is amendable at any point, and the cursor is what makes that safe.** People change their minds *because* they have seen the thing running — that is the premise of the mode — so changing the plan is as ordinary as giving feedback and goes through the planning stage's **amend path** (read first, show what changes, re-confirm — the same shape `ba-spec` uses for the brief), never a second command or a flag. **`At:` splits the plan in three:** ahead of it anything may be added, dropped, reordered or re-scoped; the current milestone's *unticked* tasks may change; **behind it nothing may** — a ticked task is a thing that exists and runs, and editing it is not amending a plan but misdescribing what happened. A change that reaches shipped code is named out loud as one of two other operations (a new task that removes it, or § Undo) rather than absorbed silently. Four rules ride on every amendment: **show the whole milestone list, not the delta** (they judge a sequence; the shape is what they can assess), **re-check the two-way `Delivers:` trace** (a drop is the commonest way a brief line becomes a promise nobody is keeping), **drop the ledger and stand-in rows with the code** (a row outliving its code makes hardening prove something that isn't there), and **re-fire the graduation check**. Every amendment leaves a Log line carrying its *why*, for the journal's reason: the milestone list records what the plan is, and only that line records why it stopped being what it was. **Three doors, all of them just saying so**: a milestone-boundary gate at the top of an iteration (*go / change something first* — the one pause inside a stage that otherwise never pauses, placed where the owner's information has actually changed, and deliberately *not* asked on a mid-milestone resume where the question has no content), feedback classified as **new** that they want now, and — the door that closes the mid-milestone gap — **anything typed after the command**. That reverses `$ARGUMENTS is ignored` without reintroducing flags: a flag is something you must learn, a sentence is not, so free text is read as *intent*, in their language, routed by meaning, and **never starts work** — it routes to a conversation, never to a `coder`, a commit, a tag or an undo, so the worst outcome of a misread sentence is one wasted question. Bare invocation is unchanged, and someone who never types anything after the command has learned nothing.
  - **Feedback is classified out loud — fix / follow-up / new.** A non-technical person cannot be expected to distinguish *that's broken* from *I want more*, and that conflation is the single biggest reason small projects never finish. Three parked items trips a **brief-drift check** (re-enact `ba-spec` against the existing brief), fired at the moment the owner has the most context they will ever have: they have just watched the thing run.
  - **Harden fires at the *share* moment**, not at some abstract end. "Tests are good practice" persuades nobody; "you're about to let other people use this" persuades everybody — and a deploy is refused while the ledger has uncovered rows.
  - **Graduation, never a hard block:** more than six milestones, one task failing three iterations, or a request vibe structurally can't serve (several people, staged releases, an audit trail) → say so and offer the full loop. The brief carries over unchanged; the decisions carry over as prose `architect` can promote into ADRs.
- **Discovery has one implementation, shared by two skills — and it is a spec, not an agent** (`skills/vibe/ba-spec.md`, read by `vibe` and `roadmap`, exactly as `plan-spec.md` is shared by `plan` and `replan`). There is deliberately no `/devloop:brief` command: what has to be reachable from every mode is the **artifact** (`.context/product-brief.md`, a shared project record), not a third command. And it cannot be a subagent — the whole thing is a conversation, agents in this plugin do not talk to the user, and a re-invoked reasoning agent shares no memory with the previous call, so a five-turn discovery would be five strangers with a shared file. The format exists because **prose does not fail**: a paragraph describing a product reads as correct to both parties while each pictures something different, and the user cannot say so without admitting they lost the thread — so every section is chosen for where a mismatch becomes *visible* (the domain **nouns** in their words, **named people** rather than roles, **one scenario** with an occasion, and the **NOT list**, which is the most falsifiable section in the document and the one most briefs omit). Method: **two or three questions, then a whole drafted brief they correct**, with `⚑` on every guess — people are far better at correcting a wrong concrete thing than authoring from blank, and interrogation is what makes a non-technical user give up or start guessing to be helpful. The nouns pay twice: they become the code's vocabulary, so the app's internals speak the owner's language — which is also why the brief is **written on disk in the owner's language** rather than the repo's (a document whose method is *they correct it* and whose signature is `Last confirmed:` cannot be stored in a language they cannot read, or it is two documents that drift with nothing to catch it) and why a differing code language forces the identifier column described in the `vibe` bullet. `ba-critic` is the mute check on a comfortable conversation producing a comfortable, wrong brief — it returns what isn't checkable *plus the question that settles it*, and its findings are turned into questions, never pasted at the user.
